# 002 · 预览通道两个验证陷阱：增量刷新不重置页面状态、应用首帧日志捕获不到

**症状**：

1. 直接改共享存储（或应用外部写入）后再用 `preview action=app` 增量刷新，页面仍显示刷新前的旧列表，与存储里的真实内容不一致——容易误判为「持久化没生效 / 存错了」。
2. `pages/home.html` 里工厂函数与 `ready()` 中的 `console.log`（如 `[init]`、`[storage] 已读取待办`）在 `preview action=console` 里始终看不到；但同一文件里交互时才触发的日志（`[todo] 新增`、`[storage] 已保存待办`）能正常看到——容易误判为「埋点没执行 / 代码没部署」。

**根因**：

1. 增量刷新会复用已存在的页面实例，`ready()` 不一定重跑，页面 data 仍是旧的；存储其实已经写成功。
2. 应用文档里的日志要等该应用的调试代理挂钩 `console` 之后才进入预览通道；页面工厂 / `ready()` 的首帧日志早于这个时点，就直接丢了（`[ServerManager]`、`[bridge-link]` 这类宿主侧日志不受影响，所以看起来「通道是通的」）。

**正确姿势**：

- 验证「初始化读取了正确数据 / 持久化真的生效」时，**不要只看增量刷新后的 DOM**：用 `eval` 执行 `location.reload()` 硬刷新后再读 DOM；或直接 `await import("/nos/storage/main.js")` 读存储真实值，两边对照。
- 判断首帧代码到底跑没跑，用**侧信道**而不是日志：例如在工厂里挂 `window.__todoInitCount = (window.__todoInitCount || 0) + 1`，刷新后 `eval` 读它；或直接读渲染结果 / 存储值。`[init]` 这类埋点保留在代码里（真实浏览器控制台看得到），但不要依赖它在预览通道里出现。
- 记录时间线对比日志时先记下 `latestTs`，事后用 `since` 增量拉取，避免被 `[bridge-link]` 噪声淹没。
