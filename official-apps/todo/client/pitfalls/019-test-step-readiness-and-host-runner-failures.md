# 019 · 用例步骤要「等页面复活」再动：reload 窗口里的选择器等不到、就绪锚点不能挑可能为空的节点

**症状**：宿主跑 `client/test/` 时报出两类错误（同一批用例，名字是短功能名）：

- `[测试] 添加任务：调试指令投递失败（预览页无响应）：ACK timeout after 4 retries`
- `[测试] 删除倒计时 / 编辑任务：调试指令 wait 等待结果超时（25000ms）`

表面看像用例逻辑错或应用卡死，但**用同一套步骤在页面里手动回放全部 8 个用例都是通过的**（应用行为没问题），说明问题出在「步骤与页面的时序」上。

**根因**（两条独立原因，都是本回合重构时新引入的）：

1. **`reload` 后面直接跟「选择器 wait」= 在页面还没复活的窗口里发指令**。重构时把上一版用例里的 `{"reload": true}, {"wait": 900}`（数值等待）换成了 `{"reload": true}, {"wait": {"selector": ".add-group-btn"}}`。`reload` 会断开调试桥、重注入代理；紧跟其后的**选择器 wait 需要把指令投递到页面**，此时页面正在重载 → 投递失败重试 4 次 → 报 `ACK timeout`；即使送达，也可能在页面重建 shadow 树的窗口里一直查不到元素 → 报 `wait 等待结果超时（25000ms）`。旧的数值等待是**宿主侧睡眠**，不需要投递，所以从来不会撞这个窗口——上一版用例一直用数值等待并不是随手写的。
2. **就绪锚点选了一个「合法地可能不存在」的节点**。我在 eval 里加了 `await T.ready('.item')` 作为「刷新后页面已就绪」的守卫，但列表在**已归档视图 / 垃圾桶视图 / 清空后**合法地没有任何 `.item`——这个守卫在这些场景里**永远不会满足**，3 秒后抛「页面就绪超时，找不到 .item」。本地回放时就是这样在「归档项删除后去垃圾桶还原」那一步炸掉的（`页面就绪超时，找不到 .item`）。改用常驻节点 `.shell` 后立刻通过。

**正确姿势**：

1. **每个 `reload` 之后先放一个宿主侧数值等待**（本项目用 `{"wait": 1500}`），让页面重载 + 代理重注入完成；**不要**把选择器 wait 紧跟在 `reload` 后面。
2. **把「等条件成立」的轮询写进 eval（页面侧）**，锚点选**页面渲染后必然存在的容器**（本项目是 `.shell`），例如：
   ```js
   T.ready = async (sel, ms) => { const n = Math.ceil((ms || 3000) / 100);
     for (let i = 0; i < n; i++) { if (T.q(sel).length) return true; await new Promise((r) => setTimeout(r, 100)); }
     throw new Error('页面就绪超时，找不到 ' + sel); };
   // 用法：await T.ready('.shell');  ← 永远存在；不要用 .item / .gitem.active 这类依赖数据的节点
   ```
   需要「等某个数据相关节点出现」时，也要先用 `.shell` 等就绪，再断言数据。
3. **长等待（倒计时 5–6 秒）单独占一个数值 wait 步骤**，不要和别的 eval 混在一条指令里：混着执行时单条指令的页面侧总耗时会被叠加上去，容易顶到调试桥的 30s 上限（本地回放实测被 30s 超时打断过一次）。
4. 断言失败 / 超时中断时用例尾部的 restore 不会执行，**跑完必须核对** `__todo_test_dirty` 已清、存储里用户数据已回来（见踩坑 018 的同名提醒）。
