# 017 · 用例断言要按实现的真实语义写：旧「拖拽排序」用例把落点语义写反了

**症状**：重构后的 `test/drag-order.test.json` 第 6 步（`T.drag('A','C','after')` 后断言顺序为 `B,C,A`）直接失败：实际得到 `C,A,B`。表面上像「拖拽功能坏了」，其实应用行为完全正确，是用例断言错了。

**根因**：起始列表顺序是 `C,B,A`（新增项置顶）。用例作者的直觉是「把 A 拖到 C 的 after 就应该是 A 落到 C 下面一格（B 之上）→ 显示成 B,C,A」，但本应用的落点判定是**按行的上/下半区**（CONTEXT「使用指南」第 7 条）：指针落在某行的**下半区**时，落点是「插到**下一行**之前」——所以 `after C` 实际是插到 C 与 B 之间，结果 `C,A,B`（`C,B,A` 才是「插到 B 之后 / 追加末尾」）。

判定方法（本次用过、以后照用）：先在预览里实测真实行为再做断言——

```js
// 依次拖 A 到 C 的上半区 / 下半区，看顺序怎么变
const cls1 = await drag('A', 'C', 'before'); // 命中行带 class "item drop-before" → A,C,B
const cls2 = await drag('A', 'C', 'after');  // 命中行无 drop 类（提示线画在下一行）→ C,A,B
```

**正确姿势**：
1. 用例失败先分清「实现坏」还是「断言错」——用 preview 直接量一次真实行为（顺序 / class / 文案），**不要先改应用代码**；
2. 断言的措辞要写清语义（如「拉到首行上半区应插到该行之前」「拉到末行下半区应追加到末尾」），别只写 `before` / `after` 这种带着作者直觉的字段名；
3. 本次已按真实语义修正 `drag-order` 的断言（`before C` → `A,C,B`、`after 末行` → 追加末尾、`before B` → `C,A,B`），并在 desc 里写明落点语义，避免下次又被「直觉」带偏。
