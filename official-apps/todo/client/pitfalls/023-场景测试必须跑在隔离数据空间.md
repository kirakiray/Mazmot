# 023 · 场景测试直接清空并覆写「正式数据空间」、多用例共用一个备份键 → 把用户真实数据冲掉了

**症状**：跑完一轮 `action=run-tests`（全套）后，用户原有的待办数据消失，存储里只剩某条**测试用例自己造出来的数据**（实测只剩一条 `周报（最终）`——那是「编辑任务」用例里的条目）。表面看像是用例写法有 bug，其实是**测试与用户数据共用同一个存储空间**这件事本身的缺陷。

**根因**：本项目的用例约定是「wipe 先备份 + 清空，restore 再还原」，且备份固定在同一个键 `localStorage.__todo_test_backup_v1`。这套机制只有在**用例严格串行**时成立：一旦两个用例重叠执行（宿主并行跑文件、或上一轮失败后下一轮紧接开始），就会互相踩：

1. A 用例 wipe：读到 `dirty='1'` → 还原上一轮留下的备份 → **再把这个内容当作新备份写回** → 清空 → 开跑；
2. 与此同时 B 用例 wipe：也读到 `dirty='1'` → 还原 → 覆写备份 → 清空 → 开跑；
3. 两边都把对方的中间态当作“待还原的用户数据”写进同一个备份键；
4. 其中一个用例失败的瞬间，`dirty` 标记与存储内容已经错位——下一个用例的 wipe 会把**另一个用例正在用的数据**当成“用户原数据”备份下来；
5. 于是备份链的锚点被替换成测试数据，链尾 restore 还原出来的就是 `周报（最终）`，**用户真实数据再也回不来了**。

（本次还伴随一个误导性现场：某用例报「刷新后应有 1 条任务，实际 0」——那正是并行 wipe 清空存储的瞬间被它撞上。看到这种“数据凭空少了”的断言失败，先怀疑并行，而不是应用逻辑。）

**正确姿势**：

1. **测试必须跑在与正式数据隔离的存储空间里**，而不是“在正式空间上备份 + 回滚”。本项目做法：应用模块顶部计算 `STORE_ID` 时先看 `sessionStorage.__todo_store_id`（`{ id, exp }`，10 分钟有效），有则改用该空间；用例的 wipe 第一步写入 `{ id: 'conjure-todo-app-test', exp: Date.now() + 600000 }` 并 `reload`，restore 最后 `sessionStorage.removeItem('__todo_store_id')` 切回。这样**即使用例全崩、备份链全乱，用户数据也一个字节都不会动**（隔离空间里的残留可以在下次 wipe 里随手清掉）。
2. 用例里**任何直接读写存储的步骤**（crafted 数据、查落盘结果）都必须用隔离空间 id——漏一处就等于又把指针指回正式空间。
3. 别把“有备份 → 一定安全”当默认前提：备份与还原都依赖共享的全局状态时，多实例并发就是数据事故，代价是用户数据。要隔离，不要回滚。
4. 排查时先核对：`getStorage('conjure-todo-app')`（正式空间）里的内容是否与用户预期一致；再用 `localStorage.__todo_test_backup_v1` 看备份链被写成了什么——备份里出现**用例刚创建出来的条目文本**，基本就能确认是链被污染。

## 追加：宿主 runner 的调试指令会**迟到数分钟**，所以隔离是唯一可靠防线

改完隔离、推送完之后的一次核查又发现正式空间里出现了 crafted 数据（`今天甲 / 今天乙 / …`，`archivedAt` 恰是当次操作时刻）。查 `preview action=console` 的原始日志发现真相：

```
[14:36:55.451] [debug] [bridge-link] recv { "msgId": "m-1791699652306-198" }   ← 十分钟前创建的指令
[14:36:55.451] [debug] [bridge-link] sent { "msgId": "m-1791700615450-20" }
[14:36:55.453] [debug] [bridge-link] recv { "msgId": "m-1791699680305-208" }
```

即：**上一轮测试运行留下的指令在十分钟后成批送达并被执行**（同一秒里接连 recv 一堆旧 msgId）。如果这些迟到指令来自**改动前**的用例（还在用正式空间 id），它们依旧会直接改写用户的正式数据；而它们对应的 restore 早就不来了。

由此得到两条硬性做法：

- **不要在“刚推完”或“刚跑完”的瞬间就宣布数据安全**：推送 / 跑测试之后留一段时间（几十秒以上）再核查正式空间，因为迟到的旧指令可能还在路上（本项目两次反复恢复用户数据，第二次就是被这个迟到批次打掉的）。
- **示例：**跑完一轮后连续核查两次（间隔 ≥ 20s）都一致，才能认为本轮真的结束了。
- 同理，`run-tests` 报告里的随机一条「调试指令 eval 等待结果超时（30000ms）」很可能是这种滞后导致的，**不代表用例或应用坏了**（实测同一轮里每次失败的都是不同用例，重跑即绿）；判断回归要看同一用例是否稳定复现。
