# 025 · 用例里的脆弱假定：用下标取行内按钮 / 断言写死多行框的整块值

（原标题：用例里用下标取行内按钮，UI 少一个按钮就静默错位）

**症状**：改 UI（去掉列表行上的铅笔按钮）之后，界面上一切正常、应用也没有报错，但几个用例的「删除」助手会点到空 / 点错元素，跑起来报 `元素不存在`，或者看着通过了但操作的是另一个按钮。本轮 4 个用例（删除倒计时 / 垃圾桶清理 / 归档桶跟随分组 / 归档链路）里都写着同一句：

```js
T.del = (t) => T.click(Array.from(T.need(t).querySelectorAll('.item-actions st-icon-button'))[1]);
```

它靠「行尾操作区里的**第二个**图标按钮是删除」这个隐含前提工作。

**根因**：下标选择器把「按钮的顺序 / 数量」当成了契约，而这个契约既不在 HTML 里、也不在报告里——UI 一改（编辑按钮被合并进「任务详情」弹窗）就变成：`[1]` 取到 `undefined`（`T.click(undefined)` 抛「元素不存在」）或取到别的按钮。更隐蔽的是 `expect` 之外的断言不会因此变红，所以这类错位很容易被当成宿主抖动放过。

**正确姿势**：
- 用例里取行内按钮**一律用语义选择器或文案 / `title` 挑**，不用下标：
  - 只剩一个同类按钮时：`T.need(t).querySelector('.item-actions st-icon-button')`；
  - 有多个时按可访问名称挑：`Array.from(row.querySelectorAll('st-button')).find((b) => T.tx(b) === '取消归档')`。本项目其它地方（`T.dlgBtn` / `T.itemBtn`）早就是这个写法，行内删除助手是仅存的下标用法，本轮已统一改掉。
- **删掉 / 新增一个行内按钮、改变按钮顺序时，先把用例里的选择器扫一遍**（改 `pages/*.html` 的模板结构后，`grep -n "item-actions"` 一类检索要连 `test/*.json` 一起查），不要等跑测试时才发现。
- 同类前提还有：断言不要依赖「按钮在 DOM 里的位置」，只依赖它的文案 / `title` / 语义类名。

## 同源的脆弱假定：断言写死了元素结构 / 整块值

**症状**：编辑区从「标题单行框 + 描述多行框」合并成「一个多行框」后，归档链路用例里的这句断言挂了（值多了一截）：

```js
const tb = d.querySelector('.edit-field');
if (tb.value !== '任务A') throw new Error(...);   // 实际是 "任务A\n描述A"
```

**根因**：多行框的 `value` 是**整块文本**（首行标题 + 其余描述），而该用例给任务带了描述。断言把“编辑框里只有标题”当成了前提，这个前提在「多行框 + 任务带描述」下不成立。它会**在改 UI 时反向暴露为假失败**——功能正确、用例报错，很费时间。

**正确姿势**：
- 断言多行框里的标题：用 `value.split(String.fromCharCode(10))[0]`（首行）或 `value.indexOf('任务A') === 0`，不要用全等；
- 需要断言“只有标题”时，**构造无描述的数据**（本项目 `T.addTask(t)` 不传第二参即无描述），别指望已有数据恰好符合形状；
- 改动输入框结构（单行↔多行、一框↔多框）后，回头扫一遍用例里对该元素的 `value` 断言——同一元素的语义变了，断言的前提往往也跟着变。
